PassKey Pairing API

A third pairing method alongside QR and Pair Code. Uses WebAuthn assertions and X25519 Diffie-Hellman to link a companion device — no QR scan, no SMS code.

Protocol

How the handshake works

The Shortcake protocol has two server-initiated rounds before pairing completes. Your app responds to WA notifications and either resolves assertions automatically (via a PasskeyAuthenticator) or hands control back to the user.

WA → passkey_prologue_request
Server sends a WebAuthn challenge. Baileys fetches WebAuthn options and a server-issued pairing ref (baked into the HKDF salt) via internal IQs, then fires pairing.passkey-request (manual mode) or resolves the assertion automatically (auto mode) and sends the prologue IQ back.
WA → crsc_continuation
Server replies with its ephemeral public key and a nonce. Baileys sends a companion_nonce IQ, completes the X25519 DH exchange, derives the encryption key and verification code, then emits pairing.passkey-confirmation with a "XXXX-XXXX" code.
App confirms → encrypted pairing request sent
If skipHandoffUx is true (re-link path), the encrypted identity bundle is sent automatically. Otherwise your app calls sock.confirmPasskeyCode() after the user verifies the code on both devices.
WA → pair-success
Standard Baileys pair-success flow. Credentials are saved, the rotated ADV secret key is persisted, and the connection restarts.

Pass a PasskeyAuthenticator implementation. Baileys resolves the WebAuthn assertion internally — your app only needs to confirm the 8-digit code when prompted (or skip it entirely if skipHandoffUx is true).

typescript my-bot.ts 
import makeWASocket, { PasskeyAuthenticator, PasskeyAssertionRequest, PasskeyAssertion } from '@whiskeysockets/baileys'

// Implement PasskeyAuthenticator using your platform's WebAuthn layer
const myAuthenticator: PasskeyAuthenticator = {
  async getAssertion(request: PasskeyAssertionRequest): Promise<PasskeyAssertion> {
    // request.rawOptionsJson is the verbatim JSON from WA — forward it to
    // navigator.credentials.get() or your FIDO2 library
    const credential = await navigator.credentials.get({
      publicKey: JSON.parse(request.rawOptionsJson),
    }) as PublicKeyCredential

    const response = credential.response as AuthenticatorAssertionResponse
    return {
      credentialId:  Buffer.from(credential.rawId),
      assertionJson: Buffer.from(JSON.stringify({
        authenticatorData: Buffer.from(response.authenticatorData).toString('base64url'),
        clientDataJSON:    Buffer.from(response.clientDataJSON).toString('base64url'),
        signature:         Buffer.from(response.signature).toString('base64url'),
      })),
    }
  },
}

const sock = makeWASocket({
  auth: state,
  passkeyAuthenticator: myAuthenticator,  // ← enables PassKey pairing
})

// Show the verification code to the user
sock.ev.on('pairing.passkey-confirmation', ({ code, skipHandoffUx }) => {
  if (skipHandoffUx) {
    // Code confirmed automatically — pairing is proceeding
    console.log(`Pairing in progress...`)
    return
  }

  // Display code and wait for user to confirm on phone
  console.log(`Verify this code on your phone: ${code}`)

  // Once user confirms both sides show the same code:
  sock.confirmPasskeyCode()
})

sock.ev.on('pairing.passkey-error', ({ error }) => {
  console.error(`Passkey pairing failed: ${error}`)
})

Omit passkeyAuthenticator. Baileys emits pairing.passkey-request with the raw WebAuthn challenge JSON — your app resolves it and calls sock.sendPasskeyAssertion(assertion) to continue.

typescript my-bot.ts 
const sock = makeWASocket({ auth: state })  // no passkeyAuthenticator

// Step 1 — WA sends a WebAuthn challenge; your app resolves it
sock.ev.on('pairing.passkey-request', async ({ requestOptionsJson, deviceId }) => {
  console.log(`Challenge from device ${deviceId}`)

  // Resolve via your platform (browser, native app, FIDO2 lib…)
  const assertion = await myFido2Lib.getAssertion(requestOptionsJson)

  // Feed the assertion back to Baileys to unblock the flow
  await sock.sendPasskeyAssertion({
    credentialId:  assertion.credentialId,
    assertionJson: assertion.assertionJson,
  })
})

// Step 2 — DH complete; show the code to the user
sock.ev.on('pairing.passkey-confirmation', ({ code, skipHandoffUx }) => {
  if (skipHandoffUx) {
    // Baileys already sent the encrypted pairing request automatically —
    // do NOT call confirmPasskeyCode() here, that would double-send.
    console.log('Pairing in progress (handoff UX skipped)')
    return
  }

  showCodeToUser(code, () => {
    sock.confirmPasskeyCode()  // called when user taps "Confirm" in your UI
  })
})

sock.ev.on('pairing.passkey-error', ({ error, isContinuable }) => {
  console.error(`Passkey error: ${error}`)
  // isContinuable is always false in this version
})

A headless Node.js authenticator backed by Redis — no browser, no native dependencies. Stores a P-256 key pair in a Redis hash and builds the WebAuthn assertion manually using node:crypto. Requires ioredis.

Prerequisite

The credential must be pre-registered with WhatsApp using this same key pair. A software key cannot be extracted from a hardware authenticator — this pattern suits development, testing, or controlled deployments where you own both the registration and the assertion.

Step 1 — Create and store the credential

Run once. The returned credentialId and publicKeyDer are what you submit to WhatsApp during the passkey registration flow.

typescript redis-authenticator.ts 
import { createHash, createPrivateKey, generateKeyPairSync, randomBytes, sign } from 'node:crypto'
import { Redis } from 'ioredis'
import type { PasskeyAssertion, PasskeyAssertionRequest, PasskeyAuthenticator } from '@whiskeysockets/baileys'

const REDIS_KEY = 'baileys:passkey:credential'

/** Run once — returns the data needed to register the credential with WhatsApp. */
export async function createSoftwareCredential(
  redis: Redis,
  rpId = 'web.whatsapp.com',
): Promise<{ credentialId: Buffer; publicKeyDer: Buffer }> {
  const { privateKey, publicKey } = generateKeyPairSync('ec', { namedCurve: 'prime256v1' })
  const credentialId = randomBytes(32)

  await redis.hset(REDIS_KEY, {
    credentialId:  credentialId.toString('base64url'),
    privateKeyPem: privateKey.export({ type: 'pkcs8', format: 'pem' }) as string,
    rpId,
    counter: '0',
  })

  return {
    credentialId,
    publicKeyDer: Buffer.from(publicKey.export({ type: 'spki', format: 'der' })),
  }
}

Step 2 — Build the authenticator

typescript redis-authenticator.ts 
export function makeRedisPasskeyAuthenticator(redis: Redis): PasskeyAuthenticator {
  return {
    async getAssertion(request: PasskeyAssertionRequest): Promise<PasskeyAssertion> {
      const fields = await redis.hgetall(REDIS_KEY)
      if (!fields?.credentialId) {
        throw new Error('Credential not found in Redis. Run createSoftwareCredential() first.')
      }

      const options = JSON.parse(request.rawOptionsJson)

      // clientDataJSON — mirrors what a browser would produce
      const clientDataJSON = Buffer.from(JSON.stringify({
        type:        'webauthn.get',
        challenge:   options.challenge,  // base64url, verbatim from WA
        origin:      `https://${fields.rpId}`,
        crossOrigin: false,
      }))

      // authenticatorData: SHA-256(rpId) || flags(1) || counter(4 BE)
      const rpIdHash = createHash('sha256').update(fields.rpId).digest()
      const flags    = Buffer.alloc(1, 0x05)  // UP (bit 0) + UV (bit 2)
      const counter  = Buffer.alloc(4)
      const newCounter = await redis.hincrby(REDIS_KEY, 'counter', 1)  // atomic
      counter.writeUInt32BE(newCounter)
      const authenticatorData = Buffer.concat([rpIdHash, flags, counter])

      // ES256: ECDSA-P256-SHA256 sobre authenticatorData || SHA-256(clientDataJSON)
      const clientDataHash = createHash('sha256').update(clientDataJSON).digest()
      const signingData    = Buffer.concat([authenticatorData, clientDataHash])
      const privateKey     = createPrivateKey(fields.privateKeyPem)
      const signature      = sign('SHA256', signingData, { key: privateKey, dsaEncoding: 'der' })

      return {
        credentialId:  Buffer.from(fields.credentialId, 'base64url'),
        assertionJson: Buffer.from(JSON.stringify({
          authenticatorData: authenticatorData.toString('base64url'),
          clientDataJSON:    clientDataJSON.toString('base64url'),
          signature:         signature.toString('base64url'),
        })),
      }
    },
  }
}

Step 3 — Wire into Baileys

typescript my-bot.ts 
import makeWASocket from '@whiskeysockets/baileys'
import { Redis } from 'ioredis'
import { createSoftwareCredential, makeRedisPasskeyAuthenticator } from './redis-authenticator'

const redis = new Redis()

// First run only — skip if credential already exists
if (!(await redis.exists('baileys:passkey:credential'))) {
  const { credentialId, publicKeyDer } = await createSoftwareCredential(redis)
  console.log('Register this credential with WhatsApp before pairing:')
  console.log('  credentialId:', credentialId.toString('base64url'))
  console.log('  publicKey (SPKI DER):', publicKeyDer.toString('base64url'))
}

const sock = makeWASocket({
  auth: state,
  passkeyAuthenticator: makeRedisPasskeyAuthenticator(redis),
})

sock.ev.on('pairing.passkey-confirmation', ({ code, skipHandoffUx }) => {
  if (!skipHandoffUx) {
    console.log(`Verify on your phone: ${code}`)
    sock.confirmPasskeyCode()
  }
})

sock.ev.on('pairing.passkey-error', ({ error }) => {
  console.error(`Passkey error: ${error}`)
})
Why Redis for the counter?

The WebAuthn counter guards against replay attacks and must be incremented atomically. HINCRBY is a single round-trip and safe across concurrent Baileys processes — unlike a file-based read-modify-write which would require an explicit lock.

Important

sendPasskeyAssertion and confirmPasskeyCode both throw "No active passkey pairing flow" if called outside an active flow. Only call them from inside the relevant event handlers.

Tip — credential format

The assertionJson field inside PasskeyAssertion must be a Buffer containing the JSON bytes that WA expects inside the <webauthn_assertion> BinaryNode. The node tag name and JSON schema are confirmed against the whatsapp-rust reference implementation; verify end-to-end during live testing before shipping.

Reference

Methods

sendPasskeyAssertion(assertion: PasskeyAssertion): Promise<void>

Manual mode only Feeds an externally-resolved WebAuthn assertion into the active flow, unblocking the prologue IQ. Must be called from inside the pairing.passkey-request handler (or any time after it fires and before the flow times out).

Throws Error("No active passkey pairing flow") if no flow is pending.

confirmPasskeyCode(): Promise<void>

Both modes Sends the encrypted identity bundle to WA and persists the rotated ADV secret key. Call this after the user has verified the "XXXX-XXXX" code on both devices. If skipHandoffUx was true, this is called automatically — do not call it a second time.

Throws Error("No active passkey pairing flow") if no flow is active.

cancelPasskeyPairing(): void

Both modes Aborts the active flow, zeroes key material, and emits pairing.passkey-error. No-op if no flow is active (safe to call unconditionally in cleanup code).

Events

'pairing.passkey-request'

Emitted in manual mode only when WA sends a passkey_prologue_request notification. Your handler must call sock.sendPasskeyAssertion() to continue.

{ requestOptionsJson: string; deviceId: string }
'pairing.passkey-confirmation'

Emitted after the X25519 DH exchange completes. The code field is a 9-character string formatted as "XXXX-XXXX" (8 Crockford base32 chars split by a hyphen, e.g. "A3KM-7PX2") to display to the user. If skipHandoffUx is true you can call confirmPasskeyCode() immediately without showing the code.

{ code: string; skipHandoffUx: boolean }
'pairing.passkey-error'

Emitted when the flow fails at any stage, or when cancelPasskeyPairing() is called. The flow is already cleaned up by the time this fires — no manual cleanup required.

{ error: string; isContinuable: boolean }

SocketConfig

passkeyAuthenticator?: PasskeyAuthenticator

Optional. Pass your authenticator implementation here to enable auto mode. When absent, the socket emits pairing.passkey-request for manual handling. Has no effect on QR or Pair Code pairing flows.
